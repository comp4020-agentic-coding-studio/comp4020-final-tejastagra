# Corrections

Every time the agent gets something wrong, and a check, a playtest or Tejas catches it, add an entry here. The fix must land in the harness (`CLAUDE.md`, `docs/rules.md`, `docs/design.md` or `spec/`), not only in the code. PROCESS.md cites these entries.

## Format

```
### C<number>. <short title>
- **Date:**
- **What went wrong:**
- **How it was caught:** test name, playtest, review or Tejas
- **Harness fix:** the rule, test or CLAUDE.md line added or changed
- **Commits:** the commit that showed the problem and the commit that fixed it
```

### C3. The catch-up reviewer review found an R16 gap and a log-injection gap
- **Date:** 26 October 2026
- **What went wrong:** `resolveRound` only validated the choices that were present, so after a game had already ended it still accepted a call with both choices `null`, bumped the round count and recomputed status, instead of refusing to resolve at all (R16). Separately, `formatEvent`'s value quoting escaped backslashes and double quotes but not `\r` or `\n`, so a value containing a newline could split one log line into two and forge a second event; field names were not validated either, so a key containing a space or `=` would also break the `key=value` format in `docs/logging.md`.
- **How it was caught:** the reviewer subagent, asked to review commits `8f9ad48` to `c37e4ac` as a catch-up review (they had not been reviewed when written).
- **Harness fix:** `resolveRound` in `src/engine/index.ts` now throws immediately if `state.status !== "playing"`, before looking at either choice, with a new R16 test in `spec/unit-engine-rules.test.ts` covering the both-null case. `formatValue` and `formatEvent` in `src/server/log.ts` now escape `\r` and `\n` and reject field names that do not match `^[a-z][a-z0-9_]*$`, with two new tests in `spec/unit-logging.test.ts`. A misnamed describe block ("R13 to R7") was also renamed to "R7 and R13".
- **Commits:** `8f9ad48` (engine) and `c37e4ac` (logger) showed the problem; `4367c71` fixed it.

### C4. A stranger who knew a game code could take over a seated player's connection
- **Date:** 26 October 2026
- **What went wrong:** The first WebSocket join handler let any client claim an already-occupied seat ("A" or "B") by naming it, and treated that as the real occupant reconnecting: the existing connection was sent `tab_replaced` and closed, and the newcomer took over the seat. With no identity system yet (R28 and accounts land in Phase 6), the server had no way to tell the real player from a stranger who had only read the game code off a shared link, so this broke R32 (one live connection per player, meant for the same player) and let a third party do what R36 says should get `game_full`.
- **How it was caught:** the reviewer subagent, reviewing the staged join/snapshot WebSocket slice before its commit.
- **Harness fix:** `attachRealtime` in `src/server/realtime.ts` now issues an opaque `seatToken` (a `randomUUID()`) to whichever client first takes a seat, sent back in every snapshot. A later join naming that seat must present the same token to take over the live connection; without it, the join is refused with `game_full` exactly as a genuine third visitor would be. This is a stand-in for real identity, not a replacement for it: once R28 (guest cookies) exists in Phase 6, seat ownership should move to the player's identity instead of a bearer token handed to whoever happens to hold the first connection. New tests in `spec/app-realtime.test.ts` (T6, two cases) and `spec/app-lobby.test.ts` (L5, impostor case) cover the refusal. The same review also caught a crash on non-object JSON messages (for example the literal `null`), a duplicated snapshot on first join and `clients_in_game`/`recipients` log fields counted across all games instead of per game; all three are fixed in `src/server/realtime.ts` with a covering test for the crash.
- **Commits:** found and fixed before `src/server/realtime.ts` was ever committed; `b981ef3` is the commit that added it with the fix already in place.
- **Revisit:** when R28 identity lands in Phase 6, replace `seatTokens` with a check against the joining player's guest or account identity, and remove the bearer-token stand-in.

### C5. The seatToken check from C4 failed open for an unissued seat
- **Date:** 26 October 2026
- **What went wrong:** `handleChoose`'s seat-token check (added in C4) compared the message's `seatToken` to `seatTokens.get(...)` with `!==`. For a seat nobody has joined in this server process, `seatTokens.get(...)` returns `undefined`; a `choose` message with no `seatToken` field is also `undefined`. `undefined !== undefined` is `false`, so the check passed and let a stranger who only knew the game code inject a choice for a seat they had never joined, breaking R21 and R22 (the server itself, not another player, would have been tricked into treating a fabricated choice as real) the moment the genuine player on the other seat chose and the round resolved on the attacker's fabricated column. The same review found an unawaited `game.resolve()` left a window where a second `choose` for the same round could be accepted before the first resolution's save completed (risking R25), a `Boolean(shield)` coercion that silently turned a malformed `shield` value into `true`, and several tests (N1 to N4, T1, T2) that were weaker than their names claimed, including sleep-based timing guesses and substring checks that could have false negatives.
- **How it was caught:** the reviewer subagent, asked to review this as the project's highest-stakes diff so far because it is exactly the code the no-peek promise rests on (ADR 0003).
- **Harness fix:** the seat-token check in `src/server/realtime.ts` now requires both the sent token and the stored token to be strings before comparing them, so two absences can never match; `column` and `shield` are type-checked before use. A `resolving` set now blocks a new `choose` for a game while its previous round's `game.resolve()` call is still in flight, and the resolve's promise is both awaited to completion and has its rejection handled (previously `void`, silently swallowing a failed save). `spec/app-no-peek.test.ts` was rewritten to use a message queue (no arrival-order assumptions), drop timing-based sleeps in favour of awaiting specific messages or racing a short timeout for "I expect nothing to arrive", and compare exact serialised messages between a low and a high choice (N2) rather than only lengths. A new test proves a `choose` for an unjoined seat with no token is ignored, confirmed by reverting the fix locally and watching the test fail before restoring it.
- **Commits:** found and fixed before this slice of `src/server/realtime.ts` was ever committed; `988dca0` is the commit that added it with the fix already in place.

### C6. The R18 timer review found a test timing risk, a leaked test timer, a stale constant and a silent-drop bug
- **Date:** 26 October 2026
- **What went wrong:** the first version of `spec/unit-realtime-timer.test.ts` used a 50 ms round timer, short enough that a slow test runner's own join and choose round trips could race the timer and make a test resolve for the wrong reason or flake. Its `afterEach` only closed the HTTP server, leaving each game's self-rescheduling `setTimeout` running against its in-memory database for the rest of the test run. Separately, `game-service.ts`'s `timeRemainingMs` still read the module-level `ROUND_TIMER_MS` constant instead of the `roundTimerMs` option passed into `createGameService`, so a test or future caller overriding the timer would still be told the wrong time remaining. Finally, if `game.resolve()`'s save failed, `resolveNow` in `realtime.ts` cleared the pending choices and re-armed the timer anyway, silently discarding the round's choices instead of surfacing the failure or retrying with them intact.
- **How it was caught:** the reviewer subagent, reviewing the R18 round-timer diff before its commit.
- **Harness fix:** the test timer was raised to 300ms, long enough to be reliably distinguishable from local socket round trips. `attachRealtime` now returns a `dispose()` that clears every pending timer, called from the test's `afterEach` alongside closing the server. `timeRemainingMs` now reads the `roundTimerMs` closure variable. `resolveNow` now puts the round's choices back into `pending` and does not re-arm the timer when the save fails, so a broken save stops that game's clock instead of retrying silently forever.
- **Commits:** found and fixed before the R18 timer slice was ever committed; `d3b9578` is the commit that added it with the fixes already in place.
- **Flagged, not fixed (needs Tejas):** the same review pointed out that without R19 (abandonment after 3 missed rounds in a row), a game nobody is connected to any more will keep re-arming its 15 second timer forever, writing an empty round to the database on every tick. This does not break any currently-implemented rule, but R19 is the rule meant to stop it, and R19 needs a new `Status` value ("abandoned") added to the engine contract in `docs/rules.md`, which is a change to the engine's shape rather than a bug fix. Per CLAUDE.md, a rule that is unclear or a contract change like this is a reason to ask Tejas rather than guess; R19 is deliberately not implemented yet.

### C7. The R27 forfeit review found a wrong-winner bug, an unpersisted result and a missing migration
- **Date:** 26 October 2026
- **What went wrong:** `startGraceTimer`'s callback in `src/server/realtime.ts` checked only whether the game had already been forfeited, not whether it had already been won or drawn through normal play. If a disconnected player's opponent won or drew the game while the disconnected player's 30 second grace timer was still pending (for example because R18's timer kept resolving rounds with only the connected player choosing), the grace timer still fired and told the opponent `game_over` with a forfeit result and a winner, even though the game had already ended with a real result, and even if that real result gave the win to the other player. Separately, a forfeit was never saved to the database before being broadcast (R25) and was tracked only in an in-memory `forfeited` map, so a server restart after a forfeit silently undid it: the restored game showed `status: "playing"` again and both players could keep playing a game the server had already ended (a promise 5 breach). Adding the `ended` column needed to fix this exposed a further bug: `openDb` recreated the `games` table with `CREATE TABLE IF NOT EXISTS`, which does nothing to an existing table, so opening the dev database (built before this column existed) crashed the whole server on startup with "no such column: ended", and it would have done the same to the production database on `/data` after a deploy.
- **How it was caught:** the reviewer subagent, reviewing the R27 disconnect/forfeit diff before its commit, for the wrong-winner and unpersisted-forfeit findings. The missing migration surfaced separately when the dev server crashed on restart after this change and Tejas asked for a proper fix rather than a workaround.
- **Harness fix:** `startGraceTimer`'s callback now re-checks `game.getGame(code)?.state.status === "playing"` immediately before forfeiting, so a game that has already ended on its own terms is left alone. `src/server/db.ts` gained a `saveEnded(code, ended)` method and an `ended` column, written before the forfeit is broadcast (R25), and `loadGames()` now returns each game's `ended` value so `realtime.ts` can restore the `forfeited` map on startup instead of losing it to a restart. The reconnect path for a forfeited game now re-checks the seat token before revealing the result, so a stranger cannot learn who won by guessing a seat letter. `openDb` now runs a numbered list of migrations tracked with `PRAGMA user_version`, each applied exactly once regardless of how old the database file is; CLAUDE.md now requires a migration and an upgrade test for every schema change. Added migration tests in `spec/unit-persistence.test.ts` (upgrading an old-schema database, and not re-running an already-applied migration) and new forfeit tests in `spec/unit-realtime-forfeit.test.ts` (wrong-token reconnect does not cancel or learn the forfeit; a game already won while a player was disconnected is not also forfeited; the production default grace period is 30 seconds). The grace period in the existing forfeit tests was widened from 300ms to 1000ms and a sleep-based "did it cancel" check was replaced with racing the next real message, reducing flakiness risk on a slow runner.
- **Commits:** found and fixed before the R27 slice was ever committed; `10d70fa` is the commit that added it with the fixes already in place.

### C8. Reviews of the lobby endpoints found a missing timer, unbounded creation and unbounded stored results
- **Date:** 26 October 2026
- **What went wrong:** `POST /api/games` (R34) created a game that never got its first round timer, because only the join path started timers, and nothing limited how many games one client could create, so the endpoint could fill memory and disk on the 256 MB machine. The first Quick match (R35) matchmaker stored a result for every pair in a map that was never emptied, deleted a result on its first read so a player whose response was lost was stranded outside a game that existed, and keyed its rate limit on the socket address, which behind Fly's proxy is the proxy for every player. Its L4 test could also fail on a ticket left waiting by an earlier run, and it never checked the created games could be opened.
- **How it was caught:** the reviewer subagent, reviewing the R34 diff and then the R35 diff before each commit.
- **Harness fix:** CLAUDE.md now says every endpoint that creates server state needs a rate limit and an expiry on anything it stores. R34's note in `docs/rules.md` records the creation limit and when the first timer starts. The timer now starts on first join for any game without one (test in `spec/unit-realtime-timer.test.ts`). `src/server/rate-limit.ts` limits creation (`spec/unit-rate-limit.test.ts`). The matchmaker keeps results for two minutes, then expires them, and a result can be read again (`spec/unit-matchmaker.test.ts`). Limits use Fly's client address header when present. L4 now clears a leftover waiting ticket and checks each game page loads.
- **Commits:** R34 problems fixed in `3335d09`, found before it was committed. The R35 problems were found and fixed before Quick match was ever committed.

### C11. The identity review found unlimited guest creation, sessions that never expired and a cross-site sign-in path
- **Date:** 26 October 2026
- **What went wrong:** the first identity endpoints let anyone create guests without limit, each writing a player and a session row. Sessions expired only in the cookie, so a leaked token stayed valid for ever on the server. The endpoints parsed any request body as JSON whatever its content type, so a cross-site HTML form could sign a visitor in to someone else's account or sign them out. One test compared two random 4-digit tags and could fail by chance. All of this came after CLAUDE.md already required rate limits and expiry on state-creating endpoints (C8), so the line was not enough on its own.
- **How it was caught:** the reviewer subagent, reviewing the identity diff before its commit.
- **Harness fix:** guest creation is rate limited and sessions are checked and purged by age on the server (tests in `spec/app-identity.test.ts` and `spec/unit-persistence.test.ts`). Identity requests must send `application/json` (tested with a form-style request). The tag test no longer relies on two random tags differing. ADR 0004 records the accepted behaviour: taken usernames are visible at sign-up, and a guest cookie keeps working as the account after sign-up. CLAUDE.md now says every endpoint that reads a body must require its content type, and the reviewer prompt for any new endpoint must check limits, expiry and content type together.
- **Commits:** found and fixed before identity was ever committed.
